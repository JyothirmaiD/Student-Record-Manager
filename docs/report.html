1. Executive Summary & Core Requirements

The Student Record Manager is designed to reliably store, query, validate, and manage student academic records with institutional integrity. The implementation strictly adheres to all specified core requirements:

1. Add Student

Enrolls student records with unique ID, full name, validated email, age, course/program, and cumulative GPA.

2. Validate Email using Regex

Validates syntax using an RFC 5322-compliant compiled regular expression, preventing format corruption.

3. Save Data to File

Uses atomic file replacement (os.replace via temporary buffers) to eliminate partial-write data corruption.

4. Read Student Data

Deserializes JSON records on boot, outputs ASCII table views, and supports fuzzy multi-field keyword searching.

5. Handle Invalid Input using Custom Exceptions

A specialized exception hierarchy ensures every input error (bad email format, invalid ID, out-of-range GPA, or duplicate records) is cleanly trapped and communicated without runtime application crashes.

3. Email Validation using Regular Expressions

Email integrity is guaranteed by applying a compiled regular expression in student_manager/validator.py before records can be instantiated: 

EMAIL_REGEX_PATTERN = (
    r"^[a-zA-Z0-9]([a-zA-Z0-9._%+-]*[a-zA-Z0-9])?"
    r"@[a-zA-Z0-9](?:[a-zA-Z0-9-]*[a-zA-Z0-9])?"
    r"(?:\.[a-zA-Z0-9](?:[a-zA-Z0-9-]*[a-zA-Z0-9])?)*\.[a-zA-Z]{2,}$"
)

Detailed Pattern Breakdown

Component Pattern Rule / Constraint Guards Against
^[a-zA-Z0-9] Leading character must be alphanumeric Leading symbols (e.g. .user@domain)
([a-zA-Z0-9._%+-]*[a-zA-Z0-9])? Local part symbols allowed internally Trailing dot before @ (e.g. user.@domain)
@ Single required domain separator Missing @ or multiple @@
[a-zA-Z0-9](?:[a-zA-Z0-9-]*[a-zA-Z0-9])? Domain hostname segment Hyphens at start or end of hostname
(?:\.[a-zA-Z0-9](?:[...])?)* Optional subdomains Supports cs.mit.edu or alumni.cam.ac.uk
\.[a-zA-Z]{2,}$ Top-Level Domain with ≥ 2 letters Single letter TLDs (e.g. .c) or numeric TLDs
Validation Enforcement Workflow
When an email fails regex validation, the system immediately raises an InvalidEmailError containing the offending string and a diagnostic reason. The CLI captures this exception, displays a friendly message to the user, and prompts for re-entry without program termination.

To ensure all edge cases are handled predictably, the system implements a clean, object-oriented custom exception hierarchy:

Exception Class Superclass Trigger Condition
StudentRecordError Exception Base class for all domain errors.
ValidationError StudentRecordError Base class for all input validation failures.
InvalidEmailError ValidationError Email format fails the regex test or length constraints.
InvalidStudentIdError ValidationError ID is blank, too short (<3), or contains illegal characters.

DuplicateStudentError StudentRecordError Attempting to register an already-enrolled Student ID or Email.
StorageError StudentRecordError File I/O permission failures or JSON corruption.

5. File Storage & Crash-Safe Persistence

The persistence module (student_manager/storage.py) ensures that disk operations are atomic. Typical file writes (e.g. open(file, 'w')) can truncate the target file before the write completes, which risks corrupting the entire database if the process is terminated mid-write.

Atomic Write Protocol
1. Serialize students list to JSON.
2. Write serialized data to an adjacent temporary file (students.json.tmp).
3. Flush and close the temporary file.
4. Call os.replace(tmp_path, target_path) which performs an atomic replacement supported by operating systems (Windows NTFS and POSIX filesystems).

Sample JSON Record Format

[
  {
    "student_id": "STU-1001",
    "name": "Alex Rivera",
    "email": "alex.rivera@university.edu",
    "age": 21,
    "course": "Computer Science",
    "gpa": 3.85,
    "created_at": "2026-09-20T10:15:00+00:00"
  }
]
